# Playwright 자동 플레이 QA — 1차

기준 게임은 PR #28의 `f5169308b1659913119f8b035e5998a0543c538d`다. 게임 소스·밸런스·저장 엔진은 변경하지 않는다. 기존 Playwright 1.56.1/Chromium 실행을 `@playwright/test`로 재사용한다. `test/playthrough-qa`를 별도 Draft PR로 제출하며 병합·배포하지 않는다.

## 실행과 분리

```sh
npm ci
npx playwright install --with-deps chromium
npm run test:playthrough
# 단일 환경 또는 시나리오
npm run test:playthrough -- --project=mobile
npm run test:playthrough -- fresh-play.spec.cjs
```

로컬에 설치된 Chromium을 사용할 경우 `CHROMIUM=/usr/bin/chromium`을 지정한다. 영상용 Playwright ffmpeg가 없는 로컬 환경만 `QA_VIDEO=off`를 사용할 수 있다. CI는 영상을 켠다. UI/버튼 선택자는 현재 게임 DOM을 사용하고 제품 코드에 테스트 훅을 추가하지 않는다.

서버는 `127.0.0.1:4177`의 저장소 파일만 제공한다. 기존 서버 재사용과 외부 base URL 설정을 허용하지 않는다. 각 테스트는 새로운 비영속 브라우저 context(PC 1280×800, 모바일 Chromium 390×844·터치·DPR1)에서 시작한다. 사용자 프로필, 실제 저장, S3와 정식 배포 origin에 접근하지 않는다. 외부 웹폰트는 빈 응답으로 대체하여 네트워크에 독립적인 대체 글꼴 기준으로 검증한다. 실기기·고DPR・다른 브라우저·외부 웹폰트 자체의 품질은 이 실행의 범위 밖이다.

## 시나리오와 정직한 진행 경계

| 여정 | 준비 | 실제 검증 |
| --- | --- | --- |
| 무주입 플레이 | 없음 | 첫 실행, 새 마을 버튼, 키보드/터치 이동·벽 충돌, 이동 후 E/행동으로 근접 채굴, 패널 채굴, 강철 10개 제작·판매, 50G 첫 가챠권, 인부 배치, 실제 10초 자동 저장, 수동 저장, 새로고침·최근 마을, 복원 사본과 원본 보존 |
| 후반 콘텐츠 | 시작 마을에서 골드 1천만, 자원별 10만, 제품별 5천, 미감정 유물 100개만 1회 제공 | 지역 4곳, 연구 9개, 터널 의뢰, 인부 배치·3능력 강화, 철 채굴 시설/인력 12, HQ12, 제작 시설15, 제작소8곳·첫 제작소Lv8, 18개 모든 제품의 실제 신규 제작, 자동 제작 토글, 상위 제품 판매, 첫 납품, 감정소·박물관 복구, 실제 감정·기증으로 박물관18종(유물12·표본6)·최종 장식 배치·회수 |
| 저장 메뉴 | 없음 | 격리 프로필에서 만든 수동 슬롯1~5를 탐색·저장·확인 후 덮어쓰기·삭제하고 마을 자동 저장 보존 |
| 느린 부팅 | 저장소 초기화 응답 보류 | 불투명 로딩 화면, 미완성 UI 숨김, 초기화 해제 후 정상 화면 |
| 오류·재시도 | 첫 문서의 IndexedDB 접근 불가 | 안전한 오류, 플레이 차단, 실제 재시도 버튼으로 정상 시작 |

`checkpoint.cjs`만 게임 상태를 쓴다. 이후에는 UI 입력과 읽기 전용 관찰만 사용한다. 광맥 길 찾기는 현재 좌표/충돌 가능 여부를 읽어 짧은 경로를 계산하고, PC 키보드 또는 Chromium의 실제 touch 이벤트로 조이스틱을 움직인다. 좌표 이동·직접 게임 동작 함수 호출·수동 tick 호출로 플레이를 대신하지 않는다. 모바일 버튼은 Playwright touchscreen tap, 조이스틱 드래그는 CDP Input.dispatchTouchEvent로 전달한다.

터널은 실제 의뢰 후 Playwright 브라우저 시계를 600초 전진시켜 완료 조건을 검증한다. 계약 타이머·게임 상수·해금 플래그를 수정하지 않는다. 이 시간 가속은 보고서의 단계 구분에 표시한다. 나머지 대기는 좌표, 버튼, 자원, IndexedDB 커밋 등 상태 기반이며 임의의 긴 sleep을 사용하지 않는다.

후반 재료 제공은 수 시간의 재화 획득과 밸런스를 검증하지 않는다. 준비 제품을 보유했다는 이유로 제작 통과로 판단하지 않고 버튼을 눌러 새 제품 수량이 증가하고 제작이 완료됐는지 확인한다. 현재 최상위 제품/연구/박물관 보상까지 접근하지만 모든 납품 수주·전 자원/인부/제작소 반복 강화 전체를 완주한 것으로 보고하지 않는다. 다음 수주의 긴 도착 대기는 미도달 단계로 기록한다. 전투, 고대 지하 도시, 스토리 등 `docs/HANDOFF.md` §8의 미구현 기능은 실패와 구분해 기록한다.

## 증거와 실패 처리

`work/playthrough/`에 HTML 보고서, `playwright.json`, 한국어 `summary.md`, 기계 판독 `summary.json`, 단계별 PNG, 실패 PNG, `journey.json`(준비 내역·마지막 성공 단계·관찰 상태·가독성 측정), `browser-errors.json`, 모든 테스트 trace.zip과 영상 webm을 남긴다. trace는 동작·DOM snapshot·소스를 유지하며, 영상과 겹치는 연속 화면 및 PNG 첨부의 trace 내 중복 사본은 끈다. 단계별 원본 PNG와 영상은 유지한다.

CI의 `playthrough-pc-*`, `playthrough-mobile-*` artifacts를 내려받아 HTML 보고서와 `npx playwright show-trace <trace.zip>`으로 확인할 수 있다. 작은 `playthrough-results-{환경}-*`에는 한국어 결과와 관찰 데이터, 실제 PNG/trace/video 파일의 경로·크기·개수를 기록한 `evidence-index.json`이 들어 있어 전체 영상을 받기 전에 진행 결과를 확인할 수 있다. 재시도는 0회이며 실패 이후에도 다른 독립 테스트/환경을 실행한다. 실패·timeout·pageerror·console.error·예고하지 않은 확인창은 테스트/CI 실패로 처리한다.

작은 터치 영역(<44px), 화면 밖 넘침, 텍스트 잘림, 다른 UI에 덮인 버튼은 위치·측정값·스크린샷을 가진 결함 후보로 기록한다. 기능 E2E 통과와 UX 결함 부재는 같은 뜻이 아니다. 측정 후보를 실제 스크린샷과 함께 검토하고 확정한 문제만 별도 보고한다. 보고 항목은 심각도(치명적/주요/경미/UX 개선), 재현 절차, 기대/실제, 증거, 추정 원인, 권장 수정이다.

새 workflow는 PC/모바일 matrix와 별도 기존 회귀·브라우저 job을 사용한다. 실패 시에도 artifact를 업로드하며 step summary를 남긴다. 기존 테스트와 workflow는 그대로 유지한다. Draft PR은 #28의 코드 브랜치 `codex/save-s2`를 base로 두어 테스트 변경만 검토할 수 있게 한다.
